How B was created

I shut down server A and made a snapshot of it in cPouta, then started A again. From the snapshot I launched a new instance with same flavor, network, key and security group. B got its own floating IP 195.148.21.99 (internal 192.168.1.200). The snapshot copied the whole disk so B had the same system, website and database as A. After that B was its own server and didnt know about changes on A. I turned off B's own week 2 app because B's database is read-only.

Storage and backup locations

  • Both servers: one disk, /dev/vda1 mounted on /, 77 GB, ext4
  • Website: /var/www/html on both
  • Database: /var/lib/mysql on both
  • Backups on B: /var/backups/www-from-a/<date_time>/, not inside the web root
  • Backup log on B: /var/log/www-backup.log

Users, ownership and permissions

  • /var/backups/www-from-a – root:root, 700, only root can read the backups
  • /usr/local/sbin/backup-www.sh – root:root, 755, only root can change the script
  • /var/log/www-backup.log – root:adm, 640
  • /root/.ssh/sync_ed25519 – root, 600, the SSH key B uses to connect to A as ubuntu
  • /etc/viikko4.env – root, 600, password for the app database user
  • Backup runs from root's crontab. The app (viikko4.service) runs as ubuntu.

Database users:

  • replicator on A – can login only from B's IP 192.168.1.200, only REPLICATION SLAVE
  • viikko4ro on B – only from localhost, only SELECT on viikko2.laskuri

B's database has read_only = ON so normal users cannot write to it. A's MariaDB listens only on localhost and the internal IP and port 3306 is not open to internet.

Hourly backup

17 * * * * /usr/bin/flock -n /run/www-backup.lock /usr/local/sbin/backup-www.sh

Every hour B copies A's /var/www/html with rsync over SSH to a new folder that has the date and time in the name. Every run writes OK or FAIL to the log.

Continuous replication

A writes all database changes to binary log. B connects to A as replicator, reads the log and makes the same changes to its own database. First I loaded B with a full dump from A and started replication from the log position that was in the dump.

Replication is not a backup because it copies also the mistakes right away. If something gets deleted on A it gets deleted on B too. Backups keep the old versions so you can go back to them.

Problem I solved and what I learned

Replication didnt start at first. SHOW REPLICA STATUS said Access denied for user 'replicator'. So the connection to A worked but the password was wrong, I had different password on A and B. I put a new password on A with ALTER USER and gave the same one to B with CHANGE MASTER TO MASTER_PASSWORD. After that both showed Yes.

I learned how to connect two servers together so that the second one copies the database from the first one automatically.
